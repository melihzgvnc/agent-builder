# Implementation Plan: real extractions must compile (no generic fallback)

Decision: not decomposed into FEAT artifacts. The three parts (compiler, extractor, tests) are small and coupled by one
test fixture set, so the existing implement-and-review loop runs this plan in order. Do NOT git commit. Do NOT call Freya. No live LLM calls in this step. Unit tests use FakeLLM only.

## Findings from exploration (verified by running the code)

- `compile_workflow(load_spec(spec_variant_N), tools/openapi.json)` raises `CompileError: tool 'verify_identity' has no field for 'question'` for ALL three variants (1, 2, 3), reproduced now. `spec_brief_a.json` compiles. The variant specs use API-style keys in field_map (`{"field": "field", "answer": "answer"}`) or have no field_map at all (variant 3 `close_call`, `transfer_to_agent`; variant 2 `get_account`), while the compiler only reads the semantic keys in `ROLE_FIELDS` (`customer`, `question`, `answer`, ...).
- `tests/test_task9_variants.py` never calls `compile_workflow`; it only checks JSON structure/uniqueness. That is why it is green.
- Compiler spot: `builder/compiler.py` `_Compiler.resolve_fields(role, name)` (line ~407) uses `field_map[sem]` or, when missing, `guess_field` (exact, `<sem>_id`, single `<sem>_` prefix). `question` -> API param `field` is not reachable by name guessing. It raises CompileError only for `REQUIRED_FIELDS` of verify/promise/close; optional roles are dropped by `drop_unusable`.
- openapi `verify_identity` body: `customer_id`, `field` (enum date_of_birth, phone_last4), `answer` (description mentions date/digits). `create_promise`: customer_id, product_id, amount (number), date (format date). `add_note`: customer_id, product_id, reason (enum), text. `schedule_callback`: customer_id, date, time ("HH:MM"). `transfer_to_agent`: customer_id, queue (enum). `close_call`: customer_id, outcome (enum), reason.
- Extractor: `builder/extract.py` `extract_from_texts` already passes `openapi_summary(doc)` in the user message (so the live warning "no tool API summary" came from the model's own reading of the sections prompt, which says only "field_map (semantic name to API field name)" and never lists the semantic names). `_primary` does extract + up to `MAX_REPAIRS=3` schema-validation repairs. Passes after: coverage, grounding. There is no compile step in extraction; `pipeline.stage_compile_workflow` catches any exception and calls `_compile_with_fallback`.
- Token cap: `SPEC_MAX_TOKENS = 20000`; `_Asker.ask` (extract.py ~285-340) retries when output is truncated (`stop_reason == "max_tokens"` yields "no usable JSON", switches `self.mode = "json"`, asks again). That is the double `extract_spec` call.
- FakeLLM (`builder/llm.py`): `FakeLLM(script)`; script items are consumed in order; each item is `{"tool_inputs":[obj]}`, `{"text": str}`, an Exception, or a callable(request). `llm.requests[i]` has `purpose`, `messages`, `tools`, `max_tokens`. Test pattern in `tests/test_extract.py`: `run(paths, [tool(spec), EMPTY_COVERAGE, {"tool_inputs":[{"mappings":[]}]}])`. Order of calls in a run: extract_spec, (extract_repair_N), extract_coverage (only if remaining>20; reply `{"items":[]}`), extract_grounding (only if bad values exist).

## Plan

- [ ] 1. Compiler: deterministic field_map derivation. In `builder/compiler.py` rewrite the per-semantic lookup in `_Compiler.resolve_fields` into a role-wide resolver `_derive_fields(role, name, props, fmap)` (new method, same file) that returns `dict[sem, api_field]` plus warnings.
      Algorithm (generic, no brief names; only the existing role/semantic constants):
      a. Explicit entries win when the value is a real body property (existing behaviour, keep the "which the operation does not have" warning).
      b. Alias keys: a field_map key that is itself a body property name (variants: `{"field":"field"}`, `{"answer":"answer"}`) claims that property for the semantic whose cues match it (step c) or, if no semantic matches, is simply recorded as claimed so it is not reused.
      c. Cue table `SEMANTIC_CUES: dict[str, tuple[str, ...]]` (module constant next to `ROLE_FIELDS`): question -> ("question", "field", "challenge", "check"), answer -> ("answer", "response", "value"), customer -> existing `cv.customer_id`/`customer_id`/`customer`, product -> ("product_id", "product"), amount -> ("amount", "sum"), date -> ("date",), time -> ("time",), queue -> ("queue",), outcome -> ("outcome", "result"), reason -> ("reason",), text -> ("text", "note", "notes", "comment"). Match on property name (exact, then `_id` form, then single prefix/suffix token match), keeping `guess_field` as the first step.
      d. Type/enum cues: amount must be `number|integer`; date `format: date`; `time` description mentions HH:MM; `question` and `queue`/`outcome`/`reason` prefer a property that has an `enum`.
      e. Elimination: after steps a-d, if exactly ONE required semantic is unmapped and exactly ONE body property is unclaimed (excluding the customer id field), map them. This resolves `question -> field` when `customer`->customer_id and `answer`->answer are claimed. Two or more candidates -> ambiguous.
      f. Ambiguous or nothing found for a REQUIRED semantic of verify/promise/close -> raise `CompileError(f"tool {name!r}: cannot derive field for {sem!r}; candidates {sorted(unclaimed)}; set spec.tools.{role}.field_map")` (precise, lists the candidates). Optional roles keep the existing drop-with-warning path.
      g. Every derived mapping (not taken from the spec) appends `self.warn(f"{role}: derived field_map {sem!r} -> {api!r} from the openapi ({reason})")`; partial maps keep their explicit entries and only the missing ones are derived. Also warn once when the spec's own mapping is overridden by nothing (no overriding; explicit always wins).
      Files: builder/compiler.py
      Verify: `uv run pytest -q tests/test_compiler.py tests/test_compiler_fallback.py tests/test_pipeline_compile.py` still passes, and `uv run python -c "import json;from builder.spec import load_spec;from builder.compiler import compile_workflow;s=json.load(open('tests/fixtures/spec_variant_1.json'));o=json.load(open('tools/openapi.json'));w,r=compile_workflow(load_spec(s),o);print(len(r.warnings))"` no longer raises.
