### 0.1 What `online_test` does TODAY (confirmed)
- `builder/pipeline.py:434` `stage_online_test(ctx)` is `raise NotImplementedStage()`. `NotImplementedStage` subclasses `StageSkipped`, so `run_stage` logs `online_test: skipped: not implemented`. It never touches the network.
- It is already wired: last entry of `STAGE_ORDER`, in `NETWORK_STAGES` (so `--dry` skips it with `skipped: --dry`), `REQUIRES["online_test"] = ("workflow",)`, `STAGE_BUDGETS["online_test"] = 600.0`, mapped in `DEFAULT_STAGES`. It is not in `ESSENTIAL_STAGES`, so `run_build` skips it with a DEGRADED line once the total budget is gone.
- Timeout machinery: `run_build` gives every `TIMED_STAGES` member (extract_spec and all NETWORK_STAGES) `timeout_s = min(limits[name], remaining)`. `run_stage` -> `_call_with_timeout` runs the stage on a SHADOW COPY of the context (`copy.copy(ctx)`, `results` dict copied) in a daemon thread. On completion every dataclass field except `results` is copied back and `results` is merged (merge happens before a stage exception is re-raised). On timeout the thread is abandoned and the shadow is discarded, so a late finish cannot change the real context but CAN still call the network. `TOTAL_BUDGET_S = 1500` (25 minutes, 5 under the 30 minute rule); `ctx.deadline` is a `time.monotonic()` value.
- Stages before it: `save` stores `ctx.results["saved"] = {workflow_id, agent_id, version}` via `_freya(ctx).save_workflow(ctx.slot, ctx.workflow, state_file=<root>/.freya-agents.json)`; `export` writes `<run_dir>/<slot>.workflow.json` (it runs BEFORE online_test, so a repair/rollback must re-export); `smoke_test` runs one chat turn and raises `StageSkipped` when the backend is unhealthy (it records no flag today).
- `tests/test_pipeline_compile.py::test_network_stage_order` asserts the exact client call order `dry_run, save, read_back, export, smoke_test` with a `FakeFreya` and `root=tmp_path` (no `public-test-set.json`). The new stage must make NO client call in that situation (it skips because it finds no cases file). That test must keep passing unchanged.

### 0.2 Key finding that shapes the whole design (probed live, no state changed beyond throwaway sessions)
The bank mock is closed-world. `POST /v1/practice/sessions {"case": <id>}` only accepts the 13 case ids of `public-test-set.json` (anything else answers `unknown practice case`; extra keys such as products, identity or now are ignored). There is no route to create a customer with custom account data. `GET /v1/practice/ledger/<customer_id>` returns `outcome, reason, promises, notes, callbacks, transfers, calls[], failures` for such a session customer. Each session call yields a FRESH customer with the same account.

Consequence: spec-generated cases cannot invent "plausible account data". The only way to get bank ground truth (ledger) is to BORROW ACCOUNTS: each generated case binds to a "carrier", an account entry (products, identity answers, variables, faults) read at run time from a cases file. The generated part is the customer behaviour (script) and the expected result, computed by the engine from the spec and the carrier's own account. The carrier file is `ctx.cases` (build.py `--cases`) or, when not given, `<root>/public-test-set.json` if it exists. It is runtime input, never embedded in `builder/`. With no carrier file, no bank key or no sessions, the stage skips loudly (DEGRADED) and leaves the agent untouched.

Known limit to record in the report: the mock applies its own rules for its accounts. If a spec's numbers differ from the mock's (e.g. a longer deadline), the bank may reject a value the spec calls valid. Such failures are class `expectation` (environment), not agent faults, are excluded from the score and are never "repaired".

## 1. Design decisions (rationale in one or two sentences each)

1. New code lives in three new modules, not in `pipeline.py`: `builder/online_cases.py` (pure: carriers, case generation, expectations), `builder/online_runner.py` (budget guard, bank adapter, batch runner, scoring wrapper), `builder/online_repair.py` (classification, repair registry, keep-best controller). `pipeline.py` only wires the stage. They must not import `builder.pipeline` (cycle); the stage passes plain arguments. Reason: each is unit-testable with fakes and the stage stays small.
2. Reuse, do not duplicate scoring. Import `persona_for` from `tools/run_cases.py` and `score_ledger` + `http` from `tools/score.py` (lazy import via a `load_scoring()` helper that puts the kit's `tools/` dir on `sys.path`; kit dir = parent of `builder/`). The judge verdict reading (`run["outcome"] == "pass"` else reason) is copied as 3 lines from `run_once`. `run_once` itself is NOT reused because it hard-codes sessions, personas and ledger lookups to `case["id"]`, uses the global `freya` module and prints, and has no deadline control.
3. Ground truth hierarchy: row pass = ledger pass AND judge pass (same as run_cases). For decisions (keep-best, repairs) the key is `(ledger_passes, conversation_passes)`, ledger first. Judge "no verdict" with a passing ledger is `judge_noise`: rerun that case once if budget allows, otherwise count it as a ledger pass.
4. No LLM in this stage. Cases, expectations and classification are rule-based, so the stage is deterministic, needs no model key, and is safe for unseen briefs. (Extraction model for live runs stays `BUILDER_LLM_MODEL=anthropic/claude-sonnet-5.5`; this stage does not use it.)
5. Never retry 502/504 (or any error) on the chat route. This stage uses the simulation route only; an exception from any Freya call marks the case or batch `infra` and is not repeated. The only repeat allowed is a fresh single-case simulation for `judge_noise`.
6. Repairs are limited to what is deterministic and generic (section 4). Hook/compiler bugs are CLASSIFIED and reported with evidence, not patched by blind string edits of generated code.
7. Safety of the live agent: keep `baseline` (the workflow saved by `save`) and `best` in memory. A repair is accepted only if it is strictly better on the comparison subset; ties and regressions roll back by re-saving the best workflow. The stage re-exports after any republish and rewrites `workflow.json` to the workflow that is live.
8. Output goes only to the run folder: `<run_dir>/online_test.json` (full report). The later live-run steps copy it to `results/`. Persona cache: `<root>/.personas.json` (gitignored, same `id:hash` key format as run_cases).

## 2. Constants (module-level, in online_runner.py unless noted)
- `MAX_CASES = 9`, `BATCH_SIZE = 5` (matches Freya default concurrency 5). Batch = one simulation, run strictly one at a time.
- `STAGE_SOFT_MARGIN_S = 45`: stage deadline = `t0 + STAGE_BUDGETS["online_test"] - STAGE_SOFT_MARGIN_S`, so the stage returns before `_call_with_timeout` abandons it.
- `REPUBLISH_RESERVE_S = 150` (one `save_workflow` can take up to its 120 s stage budget plus the re-export) is held back whenever a repaired workflow is live; `EXPORT_RESERVE_S = 30` otherwise.
- `DEFAULT_BATCH_ESTIMATE_S = 180`; after the first batch use `max(1.25 * measured, 60)`. A batch (or repair round) starts only if `min(stage_deadline, ctx.deadline) - now - reserve >= estimate`. `ctx.deadline is None` means no total limit.
- Simulation call: `run_simulation(..., max_seconds=240)`. `freya.run_simulation` polls forever, so call it in a daemon thread with `join(timeout = remaining - reserve)`. On timeout: mark the batch `infra` ("simulation did not finish; abandoned"), log DEGRADED, stop testing, restore if needed. An abandoned simulation keeps the workspace busy; say so in the warning.
- Mutations (`save_workflow`) re-check the deadline right before the call and are skipped if it is already past (an abandoned worker thread must never save late).

## 3. Case generation (spec-driven) and expectations (engine-computed)

Everything below reads the spec dict and the carrier; no brief value in code. Use `builder.engine` (`make_calendar`, `parse_now`, `band_for`, `deadline_for`, `check_promise_date`, `full_for`, `floor_for`, `attempt_offer`, `one_date_for_all`, `allowed_callback_dates`, `check_callback`, `aggregate_outcome`, `callback_window_gaps`) and `node_prompts.note_reason_for_close` for note expectations. Spec empty section -> that kind is skipped with a reason string (never a failure). An outcome `reason` of `''` or None becomes `None` in `expected` (as in public-test-set).

Carrier (`online_cases.Carrier`): `case_id`, `variables`, `identity`, `products`, `faults`, `product_ids`. `product_ids[i]` = the id the bank gives product i: take the distinct product ids found in every carrier's `expected.promises/notes`, sort by (length, text), map by position; a carrier with more products than known ids is unusable for multi kinds. Never write an id literal in code (contamination scan treats tokens with digits as strict).

`GenCase`: `id`, `kind`, `carrier_id`, `title`, `family`, `level`, `variables`, `identity`, `products`, `script`, `checks`, `expected` (exactly the `score_ledger` shape: outcome, reason, promises[{product_id, amount, date}], notes[{product_id, reason}], callbacks[{date,time}], transfers[{queue}]), `third_party` bool, `faults`. `as_case()` returns the dict that `persona_for` and `score_ledger` read (`brief` = a neutral label). `generate_cases(spec, carriers, limit=MAX_CASES) -> (cases, skipped_reasons)`; deterministic; carriers chosen by requirement (band containing the product's days late via `account_fields.days_late`, full/floor fields resolvable, product count, faults) preferring the smallest sufficient account; the same carrier may serve several cases (sessions are keyed by GenCase id in our runner).

Kinds in priority order (first 5 = round-1 batch 1):
1. `identity_lockout`: needs `identity.max_wrong_total` and `identity.on_failure.outcome`. Script: gives a wrong answer to every question prompt, `max_wrong_total` answers in total. Wrong value = deterministic corruption by `answer_format.kind` (date: year minus one; digits: each digit +1 mod 10; other: append a letter), guaranteed different from the truth. Spoken form of ISO dates via a month-name table. Expected: the `on_failure` outcome, nothing else. Checks include "no debt disclosed" when `disclose_debt` is false, and the on_failure sentence when present.
2. `promise_full`: customer pays the full amount today. Expected: product, `full_for`, date from `check_promise_date(today)` (today or next business day, capped by the deadline); outcome `aggregate_outcome([{promise_recorded: True}])`. Skip if status is past/invalid/deadline_unknown.
3. `date_over_limit` (clamping): needs `promise_rules.on_after_deadline == "offer_deadline"`. Customer asks for the first business day after the deadline, accepts the deadline when offered. Expected: full amount, date = the deadline (engine status `after_deadline`).
4. `amount_floor`: if `amounts.below_floor` and a floor exist: customer offers half the floor, accepts the floor when told; expected floor amount, date as in kind 2. Otherwise if `amounts.too_much` exists: customer says the full amount is too much; expected = `attempt_offer(1, ..., full_too_much=True)` amount and date.
5. `third_party_callback`: needs `callback_window_gaps(spec) == []` and `third_party.on_callback_scheduled`. Persona is not the customer (`third_party: True`), names a time: search `allowed_callback_dates` x (window start + 60 min) until `check_callback(...) == ok`. Expected: the `on_callback_scheduled` outcome and `callbacks [{date, time}]` (date YYYY-MM-DD, time HH:MM).
6. `intent_*` (up to 2, by ascending `precedence`, skipping `applies_before_verification`): trigger phrase = first of `intent.triggers`. Resolve the action path: transfer queue (if a `transfer` action), the `close` outcome/reason; an `offer_transfer` question follows its `on_decline` branch. Expected: that close ref, `transfers` from the queue, `promises` empty, `notes` per product when `note_reason_for_close(...)` returns a reason for a multi-product-notes spec (then outcome = `aggregate_outcome` of the note states). Intents without a close action are skipped. This covers the "already paid" and similar one-step intents generically, by the names the spec has.
7. `multi_one_date`: needs `multi_product.enabled`, `one_date_for_all == "cap_each_to_own_deadline"` and a carrier with 2..`max_products` products whose deadlines differ. Customer pays everything in full on one date = the latest deadline. Expected: `one_date_for_all` result per product, full amounts, outcome promise.
8. `tool_failure`: needs a carrier whose `faults` names the promise tool with `fail_first_n <= promise_rules.retries_on_failure`. Same script and expectation as `promise_full` on that carrier. Otherwise skip.

Judge `checks` strings are assembled from spec text only (opening.forbidden_before_verification words, `promise_rules.success_sentence`, `say_recorded_only_after_ok`, identity `on_failure.say`, mandated sentences for the stage). Keep the persona script in plain language; no stage directions.

## 4. Classification and repairs

Per failed case, `online_repair.classify(case, ledger, judge, spec, ...) -> Classification(klass, evidence, kind)`, checked in this order:
1. `infra`: simulation/ledger/session error, run missing, ledger `ok` false. Excluded from the score; DEGRADED.
2. `expectation`: a ledger call with a rejected result (`ok` false) whose request args the ENGINE accepts under the spec (bank disagrees with spec), or a carrier whose faults exceed what the spec allows. Excluded from the score; report only.
3. `hook`: a ledger call whose args violate the engine rules (promise date after the deadline or not a business day, amount outside [floor, full], callback outside the window, product id not in the account). Hook/compiler bug: report with evidence; no automatic patch.
4. `closing`: promises/notes/callbacks/transfers equal the expectation but outcome/reason differ, or `close_call` is missing. Compiler/hook bug: report only.
5. `behavior`: the ledger differs in what the agent chose (other valid date/amount, extra or missing promise/note, calls after lockout). Prompt class.
6. `conversation`: ledger passes, judge failed with a verdict. Prompt class.
7. `judge_noise`: judge gave no verdict.

Repair registry (deterministic, idempotent, each returns a new workflow dict plus a name; never mutates its input):
- `reminder:<tag>` (workflow-level prompt block, classes `behavior` and `conversation`): appends one `LIVE-TEST REMINDER` paragraph to the task text of the node that owns the stage (identity node for lockout/third-party kinds, negotiate node otherwise; read `_conv_node` in compiler.py for the field name). The text is assembled from spec fields only, by tag: lockout (identity `max_wrong_total`, `on_failure.say`, outcome), date_over_limit (`on_after_deadline`), amount (`too_much.offer_floor_times`, `below_floor.offer_floor_times`), multi (`one_date_for_all`), conversation (mandated sentences and verbatim rules of the stage). Marker prefix makes it idempotent; at most 3 reminders per workflow.
- `drop_optional_feature` (spec-level, reuses `selfcheck.REPAIRS` via `selfcheck.repair_spec` with a synthetic `SelfCheckResult` whose failed feature is `FEATURE_CALLBACK` or `FEATURE_NOTES`): used only when the callback or note case failed with class `hook` or `closing` in two consecutive rounds. Recompile with `compile_workflow(load_spec(fixed), openapi)`; accept the candidate only if lint has no errors and `run_selfchecks(...).failed` is not larger than before (same gate spirit as `pipeline._try_repair`). `spec.json` on disk is never edited and the extracted spec is never hand-edited.
- `expectation`, `infra`, `hook`, `closing` classes: no repair; they appear in `online_test.json` and as `trace.warn` lines so the next human/coder step can fix compiler or hooks (that fix is a code change in a later task, not done by the stage).

Controller (`online_repair.run_loop(...)`), strictly sequential:
1. Round 0: run the cases (batch 1, then batch 2 if budget allows) on the baseline. Record per-case results and `baseline_score`.
2. If any scored failure has a repair: apply at most one repair set (all applicable repairs together), `save_workflow`, then rerun ONLY the failed cases plus up to 2 passing "sentinel" cases (first passes in priority order) in one batch. Compare with round 0 on the same subset.
3. Accept if `(ledger_passes, conversation_passes)` is strictly greater; else roll back (re-save `best`). Tie = rollback. If accepted, `best` = repaired and, if budget remains and failures remain, one more round (max 2 repair rounds).
4. If the budget guard stops the loop while a repaired workflow is live but unscored, roll back to `best`.
5. A failed repair save keeps the previous workflow and logs DEGRADED. A failed rollback save logs an error with the workflow id and is reported in `online_test.json` `decision.restore_failed = true`.
6. On exit: if the live workflow differs from `baseline`, set `ctx.workflow`, rewrite `<run_dir>/workflow.json`, call `_freya(ctx).export_workflow(...)` again to `<run_dir>/<slot>.workflow.json`, and update `ctx.results["saved"]["version"]`.

Degraded rules (log with `ctx.trace.warn("DEGRADED: ...")` via `pipeline._degrade`, and in the report): no carriers file, no `FREYA_BANK_TEAM_KEY`, session creation failed, backend unhealthy flag from smoke_test, simulation timeout, budget exhausted, rollback failure.

## 6. Constraints checklist for the implementer and the reviewer
- No Brief A/B or variant-brief value in `builder/`, `build.py`, `scripts/` (dates, field names, enums, sentences, numbers, ids like the product-id prefix, category/outcome names). Everything comes from the spec, the carrier file or the engine. Test files may use fixtures.
- `tests/test_contamination.py` and `scripts/check_contamination.py` stay green after every item.
- Never hand-edit an extracted spec to make a case pass; repairs touch the compiled workflow or recompile a copy of the spec (no `coverage`), never `spec.json`.
- No edits to `tools/` or `public-test-set.json`. No git commit. No network in unit tests (fake clients only; the conftest already clears LLM env vars).
- Results JSONs under `results/`; delete unneeded `runs/` folders; `.freya-agents.json` slots `base`, `brief-a`, `brief-ab` untouched.
- pytest stays >= 616 with at least one unit test per new behaviour (cases, expectations, classification, each repair, rollback, budget guard, wiring, degrade paths).

## 7. Risks to watch
- The mock's own rules may differ from a spec's numbers (variants): shows up as `expectation`, not as agent failure; the report must say how many cases were excluded.
- `freya.run_simulation` has no timeout; the daemon-thread wrapper can leave a simulation running in the workspace, which makes the next builder simulation wait. Log it.
- One run per case is noisy (README: green once is a hint). The keep-best rule therefore requires strictly better, and a tie rolls back.
- An abandoned stage thread can still call the network; all mutations re-check the deadline first.
